# Portal — HSCT(및 향후 다른 프로젝트) 통합 UI 셸

## 0. 이 문서의 목적

여러 프로젝트(HSCT 등)를 하나의 화면 안에서 오갈 수 있는 새 프론트엔드 셸(shell)을
만드는 작업이다. 2026-09-22 워드픽 세션(1차)에서 사용자와 레이아웃·범위를 확인만 하고
**실제 구현은 진행하지 않았다** — "다른 세션에서 시작할 거라 일단 네가 얼마나 이해하는지
물어본 것"(사용자 원문)이라, 다음 세션이 이 문서 하나만 읽고 바로 구현에 들어갈 수 있게
확인된 내용을 정리해둔다. 같은 날 2차 세션에서 §3의 미확정 사항 대부분을 확정했다(§4
작업 로그 참고) — **단, 이 2차 세션에서도 구현(코드 작성)은 시작하지 않았다.**

## 1. 레이아웃 (사용자가 그림으로 직접 제시, 화면을 4등분)

```
┌────────┬──────────────────────────────────────┐
│   ①    │              ②                        │
│  로고   │         대분류(앱 선택)                │
├────────┼──────────────────────────────────────┤
│        │                                        │
│   ③    │              ④                        │
│ 중분류  │         선택한 기능이 실제로            │
│ (기능   │         동작하는 메인 화면              │
│  목록)  │                                        │
│        │                                        │
└────────┴──────────────────────────────────────┘
```

- **① 로고(좌상단)**: 클릭하면 홈으로 이동하는 버튼.
- **② 상단바(로고 오른쪽, 가로 전체)**: **대분류** — 여러 프로젝트("앱")를 나열해 어느
  것을 쓸지 고르는 최상위 메뉴. 사용자 확인: "여러 프로젝트 통합"이 맞다(HSCT 하나만이
  아니라 향후 다른 실제 배포된 앱들도 여기 추가될 예정) — 단, **어떤 프로젝트들을 정확히
  포함할지는 아직 정하지 않았고, 한꺼번에 다 정하지 않고 "필요한 내용을 하나씩" 만들어가기로
  확정**했다(사용자 원문). 지금 확정된 건 **첫 번째로 HSCT부터 시작**한다는 것뿐이다.
- **③ 좌측 사이드바(②에서 고른 앱에 종속, 세로 전체)**: **중분류** — 그 앱 안의 개별
  기능 목록. HSCT를 예로 들면 지금 `public/index.html`에 있는 섹션들이 후보:
  1. 발주 데이터 엑셀 업로드(order-export, 17컬럼)
  2. 레거시 업로드(URL·상품명·도착국 3컬럼)
  3. 일본어 상품명 → 한국어 번역
  4. 학습 데이터 직접 업로드
  5. 주문내역 재검토(AI분석실패) — order-status, 2026-09-22 신설분(가장 최근 기능)
- **④ 메인 영역(우측 대부분)**: ③에서 고른 기능이 실제로 동작하는 화면. **페이지 전체
  리로드 없이 같은 자리에서 상태가 바뀌는 방식**을 사용자가 직접 예시로 듦: "발주데이터
  업로드하고, 업로드 완료되면, 페이지가 바뀌면서 제안 결과 확인 및 편집으로 넘어간다."

## 2. 확정된 원칙

1. **기존 앱들의 주소는 그대로 둔다.** 지금의 `E:\Tools\HScodeTOOL\public\index.html`
   (및 그 API들)은 손대지 않는다 — URL도 코드도 그대로.
2. **이 포털은 HSCT와 완전히 별도의 프로젝트/저장소로 구성한다**(2026-09-22 2차 세션
   확정 — 최초 제안이었던 "HSCT `public/` 폴더 안에 정적 파일만 추가" 방식에서 변경됨).
   - **파일 위치**: 이 `WORDPICK SERVICES` 폴더(저장소 `daeanjun/WORDPICK_SERVICES`)
     안에 새 프런트엔드로 구성한다. HSCT 저장소는 전혀 건드리지 않는다.
   - **백엔드 연동 방식**: 별도 출처(origin)이므로, HSCT API는 크로스오리진으로
     절대경로 호출한다 — 운영 주소 `https://hs-code-tool-production.up.railway.app`
     (`HScodeTOOL/README.md`에서 확인). HSCT의 `server.js`에 이미 `app.use(cors())`가
     걸려 있어(전체 출처 허용) 이 방식이 코드 수정 없이 바로 동작한다 — 이 사실은
     `HScodeTOOL/server.js`를 직접 읽어 확인했다(추정 아님).
   - **CSS**: 기존 `HScodeTOOL/public/styles.css`를 재사용하지 않고, 이 저장소 안에
     새 스타일시트를 신설한다(2026-09-22 2차 세션 확정).
3. **한꺼번에 다 만들지 않고 단계적으로 간다**(사용자 명시: "앱 목록은 한꺼번에 하기보다
   필요한 내용을 하나씩 만들어가자").
   - 1단계: ①②③④ 뼈대만 먼저(정적 레이아웃) — 상단바(②)엔 우선 **HSCT 하나만**,
     사이드바(③)엔 §1의 4개 기능 목록을 넣되, ④는 아직 빈 화면/자리표시자로.
   - 2단계: **"발주 데이터 엑셀 업로드"를 첫 실제 동작 기능으로** ④에 연결한다
     (2026-09-22 2차 세션 확정 — 1차 세션에서 제안했던 "주문내역 재검토"에서 변경됨).
     나머지 기능은 "준비 중" 표시만 해두고 이후 하나씩 연결.
4. **기술 스택/배포는 아직 확정되지 않았다** — §3 참고. 오늘(2026-09-22 2차 세션)은
   계획 확정까지만 진행하고, 실제 구현(코드 작성)은 다음 세션에서 시작하기로 사용자가
   명시했다.

## 3. 아직 미확정 — 다음 세션 시작 시 확인할 것

1. **포함할 프로젝트(앱) 전체 목록**: HSCT 다음으로 어떤 프로젝트를 추가할지(예:
   wordPICK-service 등 실제 배포된 다른 Railway 프로젝트가 후보로 언급됐으나 확정 아님).
2. **기술 스택/검증 순서(2026-09-22 2차 세션 중 사용자 지시로 변경 → 같은 세션 안에서
   재변경)**:
   "처음 하는 거니까 뼈대를 로컬에서 잡고 서버로 이어가자" → 1차로 순수 정적
   (HTML/JS/CSS, 서버 로직 없음)으로 로컬에서 뼈대를 만들었다(§5 작업 로그 참고).
   이후 확인용 URL을 요청받아 GitHub Pages를 시도하는 과정에서 **Claude가 처음
   안내했던 내용이 부정확했음이 실제 API 응답으로 드러났다**: "비공개 저장소도 Pages
   배포는 되고 페이지 URL만 공개된다"고 안내했으나, 실제로는 **GitHub Free 플랜에서는
   비공개 저장소에 Pages 자체가 전혀 활성화되지 않는다**(`POST .../pages` 호출이
   `"Your current plan does not support GitHub Pages for this repository."` 422로
   거부됨). 이 사실을 다시 안내하고 재확인받은 뒤, 사용자가 **"저장소를 Public으로
   전환하고 Pages 진행"으로 확정** — 그 결과 **이 저장소는 2026-09-22부로 공개
   (PUBLIC)로 전환됐다.** 소스 코드(HTML/CSS/JS, 커밋 이력 포함)가 전부 공개된
   상태이므로, 이후 민감한 내용(내부 API 키, 실제 고객 데이터 등)을 이 저장소에
   커밋하지 않도록 주의할 것.
   - GitHub Pages는 **Actions 기반 배포**로 설정했다(`.github/workflows/deploy-pages.yml`)
     — 정적 파일이 저장소 루트가 아니라 `public/` 폴더에 있어서, 브랜치 기반 Pages
     (루트 또는 `/docs`만 지원)로는 불가능했기 때문. `master` 브랜치의 `public/**` 변경
     시 자동 배포된다.
   - 배포 URL: `https://daeanjun.github.io/WORDPICK_SERVICES/`
   - Node/Express 서버 전환은 그다음 단계로 미룬다(정적 → Express 전환은 파일 구조를
     그대로 두고 얇은 서버만 씌우면 되므로 복잡도가 낮다고 Claude가 설명했고, 사용자가
     이 순서에 동의함).
3. **배포 대상(Railway 등)은 여전히 미결정** — GitHub Pages는 어디까지나 확인용이며,
   실제 운영 배포처는 별도로 다시 논의한다.
4. 실행 게이트 원칙: 1단계(로컬 정적 뼈대) 구현은 2차 세션 중 사용자가 "뼈대를 로컬에서
   잡고 서버로 이어가자"고 명시적으로 지시해 **시작 승인을 받았다**. 저장소 공개 전환과
   GitHub Pages 활성화도 같은 세션에서 사용자가 명시적으로 확정했다. 단 이 승인들은
   여기까지이며, Node/Express 서버 도입이나 Railway 등 실제 배포는 별도로 다시
   확인받을 것.

## 4. 폴더 구조 (1단계 구현 후 기준)

```
WORDPICK SERVICES/
├── README.md          # 이 문서
└── public/
    ├── index.html      # 4분할 셸의 정적 골격(①로고 ②앱탭 ③사이드바 ④메인)
    ├── styles.css      # 새로 만든 스타일시트(HSCT의 styles.css와 무관, CSS Grid 4분할)
    └── portal.js       # APPS 데이터(HSCT 탭 1개 + 기능 4개, 전부 status:'pending')를
                         # 기반으로 탭·사이드바·메인 영역을 렌더링/전환하는 순수 JS.
                         # 서버 호출은 아직 전혀 없다(1단계 범위 밖).
```

- 서버 로직은 아직 없다(1단계는 순수 정적 파일뿐). 실행하려면 아무 정적 서버로 `public/`
  폴더를 서빙하면 된다 — 예: `npx serve public`.
- 기능 4개는 모두 `status: 'pending'`으로, 클릭하면 ④ 영역에 "아직 연결되지 않았습니다"
  안내만 표시된다. 실제 API 연결은 2단계(§2.3) 이후 작업.

## 5. 작업 로그

### 2026-09-22 (1차) — 레이아웃·범위 확인만 진행(구현 없음), 이 폴더·문서 신설

사용자가 4분할 레이아웃 그림을 제시하고 이해도만 확인 요청 → 설명 후 두 차례
AskUserQuestion으로 범위 확인(여러 프로젝트 통합 확정, 단 목록은 미정 / HSCT부터 시작
확정) → 사용자가 "일단 구현은 하지마"로 명시 중단 → "다른 세션에서 시작할 거라 확인만
한 것"이라며 이 요약 문서 작성 요청. 코드는 전혀 작성하지 않았다(기존 `styles.css`
참고차 읽기만 함).

### 2026-09-22 (2차) — §3 미확정 사항 확정 + 1단계(로컬 정적 뼈대) 구현

1. HSCT의 `public/index.html`·`styles.css`·`server.js`를 직접 읽고 실제 기능 목록(7개
   섹션 → 중복/중첩 제외하면 4개 상위 기능)과 `app.use(cors())`가 이미 걸려 있는 사실을
   확인.
2. AskUserQuestion으로 미확정 사항을 순차 확인: 첫 연결 기능(주문내역 재검토 → **발주
   데이터 엑셀 업로드**로 변경), 파일 경로(HSCT `public/` 안 → **이 저장소 자체**로
   변경), CSS(재사용 → **새 스타일시트 신설**), 구현 시작 여부(처음엔 "계획만, 구현은
   나중에"로 답했다가, 바로 다음 메시지에서 "처음 하는 거니까 뼈대를 로컬에서 잡고
   서버로 이어가자"로 번복 — 이후 답변을 우선해 진행).
3. 사용자가 "GitHub에 push해서 GitHub Pages로 동작 확인이 가능한지" 질문 → `gh repo
   view`로 이 저장소가 PRIVATE임을 확인하고, Free 플랜 기준 비공개 저장소도 Pages
   배포 시 렌더링된 페이지 URL은 공개된다는 사실을 안내 → 사용자가 최종적으로 "로컬에서
   먼저 확인"(GitHub Pages 확장은 나중 단계)으로 확정.
4. `public/index.html`·`public/styles.css`·`public/portal.js` 신규 작성(1단계 범위:
   정적 뼈대만, 실제 API 연결 없음).
5. 검증: ① `node --check`로 `portal.js` 문법 확인, ② `npx serve public`으로 로컬
   정적 서버를 띄우고 `curl`로 3개 파일 모두 HTTP 200 확인, ③ jsdom으로 `portal.js`를
   실제 DOM에서 실행시켜 탭/사이드바 렌더링과 클릭 시 ④ 영역 전환(기능명·"준비 중"
   배지·`is-active` 클래스·홈 리셋)을 assert 기반으로 검증 — 전부 통과. **단, 실제
   브라우저로 시각적 렌더링(그리드 배치·색상 등)은 이 환경에 브라우저/스크린샷 도구가
   없어 확인하지 못했다** — 사용자가 `npx serve public` 후 직접 열어보는 것을 권장한다.

### 2026-09-22 (3차) — 확인용 URL 요청 → GitHub Pages 배포(저장소 Public 전환 포함)

사용자가 "확인 가능한 URL은?"이라고 질문 → 처음엔 "로컬 실행 vs 지금 GitHub Pages 배포"로
선택지를 물었고 사용자가 "지금 GitHub Pages로 공개 URL 만들기"를 선택. `gh api POST
.../pages` 시도 결과 **"Your current plan does not support GitHub Pages for this
repository."(422)** 오류 발생 — 2차 세션에서 Claude가 안내했던 "비공개 저장소도 Pages는
되고 URL만 공개된다"는 설명이 **틀렸음이 실제 API 응답으로 드러남**(Free 플랜은 비공개
저장소에 Pages 자체가 비활성화됨). 이 사실을 정정해 다시 안내하고 재확인받은 뒤, 사용자가
"저장소를 Public으로 전환하고 Pages 진행"으로 확정 →
1. `gh repo edit --visibility public --accept-visibility-change-consequences`로 저장소
   공개 전환(확인됨: `gh repo view --json visibility` → `PUBLIC`).
2. `public/` 폴더가 저장소 루트가 아니라 브랜치 기반 Pages(루트/`docs`만 지원) 불가 →
   `.github/workflows/deploy-pages.yml` 신설(Actions 기반 배포, `master`의 `public/**`
   변경 시 자동 배포).
3. `gh api POST .../pages -f build_type=workflow`로 Pages 활성화 확인.
4. 커밋·푸시 후 `gh run watch`로 워크플로가 `success`로 완료됨을 확인, `curl`로
   `https://daeanjun.github.io/WORDPICK_SERVICES/`·`styles.css`·`portal.js` 3개 모두
   HTTP 200 실제 응답 확인.

**주의**: 이제 이 저장소는 소스 코드·커밋 이력이 전부 공개 상태다. 앞으로 API 키·실제
고객 데이터 등 민감한 내용을 커밋하지 않도록 유의할 것.
